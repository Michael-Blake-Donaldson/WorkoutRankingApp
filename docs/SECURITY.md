# Phase 1 security boundaries

## Threats and implemented controls

| Threat                      | Control                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Public/third-account signup | Allowlisted HTTP auth endpoints, email-bound expiring invitations, PostgreSQL trigger consuming invitation and allocating one of two unique slots under locked counter transaction. Database checks apply even to direct user inserts.                                                                                                                                        |
| Token theft/replay          | 256-bit invitation entropy, SHA-256 invitation hashes, hashed magic-link identifiers, five-minute single-use email proofs consumed by Better Auth. Tokens are URL fragments in user-facing links, removed from address bar after reading; no token in request URLs. Explicit confirmation avoids redemption by an email scanner GET.                                          |
| Session exposure            | Library-managed opaque database sessions, HttpOnly + SameSite=Lax cookies, Secure cookies for HTTPS, seven-day absolute expiry with sliding refresh disabled, immediate server revocation, cookie cache disabled. Browser JSON returns identity/expiry only, never a bearer token. Sessions remain sensitive database data.                                                   |
| CSRF / open redirects       | Exact configured origin for mutations and rejection of cross-site fetch metadata; Better Auth origin protection retained. Fixed callback destinations; strict input schemas reject callback injection. Native sign-out also passes through the same checks. Referrer-Policy same-origin avoids cross-site referrers while preserving native POST Origin.                      |
| XSS / embedding             | React escaping, no arbitrary HTML rendering, per-request nonce script/style CSP, strict-dynamic script policy without production unsafe-eval, frame-ancestors none, DENY frame header, nosniff, restricted browser permissions. Dynamic page rendering is required for nonces.                                                                                                |
| Brute-force/mail abuse      | Atomic PostgreSQL limits: 120 auth requests/minute globally, three email-link requests/10 minutes per HMAC email key, including ineligible addresses. Generic eligibility responses; neither IP headers nor proxy claims trusted. Global limits trade availability for a small two-user deployment. Edge request/connection limits are additionally required before exposure. |
| Excess database privileges  | Separate local runtime login: no superuser/DDL, no direct invite/capacity writes, no audit edit/delete. Fixed security-definer triggers have pinned search paths and migration-role ownership. Operator credentials remain separate.                                                                                                                                          |
| Cross-account reads         | Session-derived identity in `/api/me` and private pages; no client-supplied owner ID accepted. Private future domain endpoints must add their own ownership checks. Phase 1 does not imply that future health-data authorization is implemented.                                                                                                                              |
| Private offline leakage     | Service worker caches six fixed public assets only; no authenticated HTML, API, RSC payloads or tokens. Private responses no-store; offline page has no account data. Worker updates do not force an active page takeover. Workout IndexedDB and pending-data logout safeguards belong to Phase 5.                                                                            |
| Secret/log leakage          | `.env*`, generated local TLS keys and test traces ignored. Production env requires HTTPS and authenticated implicit TLS SMTP. Raw auth/query logging disabled. Operator invite command is the sole intentional one-time plaintext invite output. No real emails are sent by automated tests.                                                                                  |

## Production deployment gate

The implementation is locally runnable, not deployed. Proposed hosting: one Node 24 web process/container behind an HTTPS reverse proxy, managed PostgreSQL with backup/point-in-time recovery, authenticated TLS SMTP on port 465, and a daily cleanup job. A single host is sufficient initially; no vendor account, domain, paid service or external email recipient has been configured. Provider selection remains open until actual deployment.

Before exposure: configure canonical `BETTER_AUTH_URL` (origin only), independent random secret, real SMTP credentials and certificate validation, TLS PostgreSQL connection with CA verification, HTTPS termination and HSTS-compatible domain, restricted web credentials, edge body/request/time limits, privacy-safe error alerts, encrypted backups and restore procedure. Disable access/query-string/body logging at proxy and provider; email infrastructure necessarily receives the recipient and one-time proof, so choose a trusted provider and retention policy. Do not set `NODE_TLS_REJECT_UNAUTHORIZED=0`.

Create production roles with an operator-controlled secret manager. The migration owner owns schema/functions; the web role must not own objects or belong to the migration role. Production auth/session reads reject elevated roles using a database privilege probe. Reproduce the explicit table grants in `scripts/local-runtime-role.ts`, not blanket privileges/default grants on future health tables. Revoke public schema CREATE. Keep invitation issuance and session-revocation tools operator-only, with separate credentials; no admin HTTP endpoint exists. Grant maintenance only the permissions its tasks need. Application ownership checks are still required even with restricted DB grants.

Production release also requires a real iPhone installation/offline/logout check, production SMTP delivery/expiry test, database backup/restore rehearsal, and review of actual hosting proxy headers and logs. These are not marked complete by local emulation or dependency audits.

## Known limits and future obligations

Generic sign-in messages prevent direct membership disclosure but cannot guarantee identical timing, especially during SMTP failures. A global auth limiter can be exhausted to deny access temporarily; it intentionally avoids spoofable IP trust until deployment topology is known. Email account compromise compromises passwordless login; no MFA/passkey is implemented in Phase 1. Existing session revocation does not ban future logins or cancel existing valid email proofs. Browser storage and back/forward behavior need real device testing; private profile health data is now present. No workout data is available offline.

The account counter records enrolled slots and does not automatically reopen a slot after deletion. No deletion HTTP endpoint exists yet; reviewed deletion/anonymization and slot replacement policy belong to Phase 8. No broad security certification is claimed. Future phases must preserve these boundaries and extend integration tests as new private resources are added.

## Phase 2 additions

Private profile tables use forced row-level security, owner-matching child foreign keys and explicit runtime grants. Each request establishes its owner from the authenticated session and sets a transaction-local owner for database policies. Missing owner context returns no private rows. Mutations require an owner-intent header matching the session to reject stale tabs after an account switch; the header never authorizes access. Profile revisions and measurement corrections are append-only for runtime credentials. Role verification also rejects BYPASSRLS privileges.

All health forms use POST and remain disabled before hydration. Client mutations carry UUIDs and expected aggregate revisions, and unchanged measurement retries preserve their generated timestamps. Health fields and validation values are not placed in URLs, persistent browser storage or logs. API responses and private pages remain no-store; sharing consent never exposes health data through another endpoint.

The CSP retains nonce/strict-dynamic scripts and nonce-restricted stylesheets. `style-src-attr 'unsafe-inline'` is a deliberate scoped exception for Next.js's screen-reader route announcer, whose bundled implementation uses `style.cssText`. UI components render text through React escaping and never accept arbitrary HTML/CSS. Validation schemas stay server-side; dependency-free UI options avoid Zod's dynamic-code probe in the browser.

Profile measurements, restrictions, targets, equipment and version snapshots remain private even after enabling competition summary consent. Competition scoring and delivery of shared summaries are not implemented in Phase 2. Audio/haptic toggles persist preferences; they do not request device permissions or imply implemented workout alerts.
